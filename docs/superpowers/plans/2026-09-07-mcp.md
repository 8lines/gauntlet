# MCP integration plan

## Goal

Allow an AI client to discover and invoke capabilities explicitly registered by
applications, through the same non-production control plane used by testers.

## Architecture and decisions

- Mount an opt-in `/mcp` endpoint in `apps/server`, using the official MCP SDK
  and Streamable HTTP. Support current clients and stateless 2025 clients.
- Keep one fixed set of nine tools. Discover application catalogs on demand
  rather than generating tool names for every target/operation combination.
  This keeps discovery stable across application deployments and avoids name
  collisions and a large initial tool context.
- Share `ManifestService`, `RunProxyService`, the validated adapter client and
  projection store with REST. Extract data-source admission into a shared
  service. No Adapter v1 or application SDK changes are required.
- Pass explicit operation revisions, typed input, confirmation acknowledgements,
  dry-run intent and idempotency keys through unchanged. Keep application
  execution and input validation in the existing adapter runtime.
- Return structured JSON and an equivalent text block. Translate existing
  Problems into sanitized tool errors. Accepted asynchronous runs are followed
  through polling; application cancellation remains an explicit tool call.
- Cover uploads with bounded base64 input and session launch with the existing
  artifact/public-origin validation. Never fetch caller-supplied URLs or read
  server-local files.
- Default MCP to disabled. Validate Origin before parsing/dispatch, reject
  unlisted origins, and retain the existing private deployment boundary.
  Reserve `/mcp` from static files and the SPA fallback even when disabled.

## Implementation sequence

1. Add pinned official SDK packages and shared data-source service.
2. Register discovery, execution, run, data-source, upload and launch tools.
3. Wire HTTP lifecycle, startup settings, body bounds and origin validation.
4. Add opt-in settings to Compose and Helm and document client setup.
5. Verify both MCP protocol generations with an actual SDK client over HTTP;
   test shared REST history, policy failures, capability/target isolation,
   sanitization, uploads and launch; run server and distribution regressions.

## Boundaries

Authentication remains deferred consistently with the existing product. Tool
annotations and confirmation acknowledgements are not an authorization system.
No stdio executable, MCP task/session storage, automatic browser opening,
artifact downloading, or streaming run subscriptions are introduced. Existing
Adapter v1 SSE remains available through REST; MCP obtains run snapshots by
polling. The control plane continues to have process-local projection history.
